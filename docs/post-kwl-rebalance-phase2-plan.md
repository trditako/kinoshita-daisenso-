# KWL後・全キャラクター大幅リバランス 第2段階調整設計

## この文書の位置づけ

- 対象PR: #472「全キャラクター環境再構築リバランス v1」
- 対象ブランチ: `feat/post-kwl-global-rebalance-20261118`
- 本番反映: しない。KWL終了後に別途判断する。
- この段階では、根拠のない一律倍率や仮のキャラクター数値を追加しない。現行の実装・能力データ・戦闘処理を照合し、個別調整と検証条件を確定する。

## 第2段階の基本原則

1. キャラクターの強さはHP・攻撃力だけでなく、射程、攻撃範囲、攻撃頻度、移動速度、再生産、KB、妨害、耐性、回復、召喚・成長条件を含む実効性能で評価する。
2. 同じレアリティでも役割が異なるため、レアリティだけを根拠に同じ上限へ揃えない。
3. 強みを残し、弱点・編成条件・発動条件・再使用時間で個性を作る。固有ギミックを一律に削除しない。
4. 「能力」と「スキル」を別々に評価する。常時効果、編成時効果、戦闘中に条件を満たして発動する効果を混同しない。
5. 敵ステージ用データ、キャラクターID、所持情報、編成保存データ、報酬・ドロップ設定は変更対象に含めない。
6. KWL関連コード・大会中の戦闘条件には触れず、KWL終了後の適用候補として隔離する。

## 評価指標

キャラクターごとに以下を記録し、単一の「総合戦闘力」だけで結論を出さない。

- 耐久: HP、被ダメージ軽減、被ダメージ上限、回復、バリア、KB、状態異常耐性
- 火力: 1回攻撃、攻撃頻度、範囲内の期待命中数、属性特効、追加攻撃、継続ダメージ
- 射程・機動: 射程、攻撃範囲、移動速度、接近・離脱性能、対空
- 制圧: 停止・鈍足・凍結・吹っ飛ばし・拘束などの発動率、効果時間、対象数、再使用時間
- 編成依存: 編成条件、重複可否、上限、対象範囲、本人への適用有無
- 運用コスト: 出撃コスト、再生産時間、モード切替コスト、成長に必要な撃破数・時間
- 装備・レベル依存: レベル補正、装備6枠、セット効果、スキルツリー、他キャラのバフとの乗算・加算順

## 第1段階PRに対する実装前レビュー項目

PR #472 の現行ソフトキャップは暫定パスとして扱い、以下を確認するまで本番適用しない。

- `rarityCaps` のレアリティ文字列が実データの全表記と一致しているか。未知レアリティが一律fallbackへ流れていないか。
- `resist` の値が「軽減率」なのか「被ダメージ倍率」なのかを、実際に参照する戦闘処理と照合する。意味が確定するまで `resistMin` による一律変更を確定値として扱わない。
- `strong` の値が倍率・加算値・別スケールのどれかを参照元で確認し、上限値を決める。
- スキル倍率のキーが `damageMultiplier` / `multiplier` 以外にも存在しないか調べる。説明文だけに倍率があるスキルを取りこぼさない。
- `slow` などの能力オブジェクト形状がキャラクター間で統一されているか確認する。存在しない共通スキーマを仮定しない。
- 起動時に一度だけ補正されるのか、後から登録されるカードに何度適用されるのかを確認する。二重補正・登録順依存を防ぐ。
- HP・攻撃力・射程のソフトキャップが、低レアリティの役割キャラや射程特化キャラを不当に潰さないか確認する。
- レベル、装備、スキルツリー、編成バフの適用前後どの段階に補正が入るか確認し、補正順序による二重適用を防ぐ。

## 必須テスト

1. 全カードのID・名前・配列順・所持情報が変更前と一致する。
2. 実行時に最終登録された全カードが、ちょうど1回だけ調整対象として処理される。
3. 同じ初期データで起動を繰り返しても結果が変化しない（冪等性）。
4. 敵ステージの敵データ・倍率・出現時刻・報酬が変更されない。
5. 代表的な低レアリティ、射程特化、耐久特化、妨害特化、成長型、URを個別に回帰テストする。
6. 装備なし/あり、レベル1/最大付近、編成バフなし/ありを組み合わせ、異常な乗算・上限突破を確認する。
7. PvPと通常ステージの双方で、攻撃・妨害・回復・死亡・再生産の挙動を確認する。
8. キャラクター詳細の数値と実際の戦闘中の数値が一致する。

## 調整の進め方

- Phase A: 全登録キャラの現行値・能力・スキル・参照先を棚卸し
- Phase B: 役割分類（壁/近接火力/遠距離火力/妨害/支援/対属性/成長/特殊ギミック）
- Phase C: 役割別の性能基準と個別例外を策定
- Phase D: キャラクター単位の変更表を作成し、変更理由と期待する弱点を明記
- Phase E: 回帰テスト・実戦シミュレーション・詳細画面表示を検証
- Phase F: KWL終了後にのみ適用可否を判断

## 完了条件

全キャラクターについて「変更なし」も含めて判断理由が記録され、能力・スキルの参照先と効果が検証され、ID/所持/編成/敵ステージ/報酬に回帰がなく、テスト結果が確認できること。これらを満たすまではDraftを維持し、マージ・本番反映・Supabase変更・デプロイを行わない。


## 2026-11-19 実コード照合メモ（PR #472）

### 確認できたデータ仕様

- `hastur.js` の味方ハスターは `resist` を各属性 `.45` として保持し、説明文では「被ダメージ55%軽減」と定義している。敵版は `.15` で「85%軽減」。したがって、このプロジェクトの `resist` は軽減率そのものではなく、被ダメージ倍率（受けるダメージの割合）として使われている。
- `zeus.js` でも味方ゼウスの `resist` は `.45`（説明文55%軽減）、敵ゼウスは `.15`（85%軽減）。同ファイルの従者は `.05`（95%軽減）。この対応関係からも上記の意味が裏付けられる。
- `strong` は属性別のダメージ倍率として記録されている。ゼウス味方版は5倍、敵版は10倍、従者は8倍。第1段階の上限処理は、カード側の倍率を既定上限4へ圧縮する設計になっている。
- `hastur.js` と `zeus.js` は敵ボスを `enemyTypes` に登録し、味方カードを `cards` に登録している。PR #472 の走査対象は `cards` のみなので、敵ステージのボス能力値はこの補正関数から直接変更されない。

### 現行補正ロジックで数値上確認できる影響

`globalRebalanceSoftCap` は、上限以下の値にも `floorBoost: 1.04` を適用する。そのため「低すぎる値だけを底上げ」ではなく、上限以下のHP・攻撃力を原則すべて4%増加させる。これは実装コメントと実際の条件が一致していないため、個別調整前に修正判断が必要。

また、上限超過時もハード上限ではなく「上限＋超過分×比率」に着地する。例として、現行の味方ハスター（UR、HP500,000/攻撃力122,000/射程180）は、現行式をそのまま適用するとHP145,100、攻撃力31,800、射程180となる。これは計算上の予測値であり、ブラウザ実行での反映確認値ではない。

味方ゼウスは `atk` だけでなく `multiAttack` と `zeusAlly.bands` に各雷撃ダメージが別途定義されている。カードの `atk` を圧縮しても雷撃帯の数値は同じ処理では自動的に圧縮されない可能性があるため、雷撃ダメージの参照元とレベル補正処理を確認してから個別調整する。ゼウスは通常の単発攻撃キャラとして `atk` だけを調整してはならない。

### 次に行うべき修正・検証

1. `floorBoost` を「低すぎる値の下限補正」として使うのか、全キャラへの4%強化として使うのかを明確化する。現状のままでは後者になる。
2. 味方ハスター・味方ゼウス・アイスワイバーン・創世木下など、固有能力や専用攻撃データを持つキャラは、汎用HP/攻撃力補正後の実効値を専用処理側と突き合わせる。
3. `resist` の意味は被ダメージ倍率として確認できたため、今後の仕様書では「被ダメージ倍率の下限」と表記し、「軽減率の下限」と誤記しない。
4. `cards` 登録後に同じカードの `ability` を再構築するモジュール（特に `genesis.js`）では、WeakSetによる一度きり処理だけでは後から追加・上書きされた能力値を再評価できない。カード登録完了後の最終確定タイミングと、補正済みデータの再処理方針を分けて設計する。
5. `scripts/export-character-roster.mjs` は最終カード数との一致を検査するが、能力・スキルの後書き変更や専用攻撃データの補正漏れまでは検査しない。ロスター数一致をもってリバランス完了と判定しない。

※ここで記録したのはソースコード上の定義と計算式の照合結果。ブラウザでの実戦挙動、装備・レベル・編成バフ込みの最終値は未検証。
